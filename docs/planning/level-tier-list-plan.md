# 레벨별 채보 서열표 구현 계획

> 2026-09-24 변경: 모델·지원 레벨·등급 정책은 [CPI·SPI·개인차 분석 계획](cpi-spi-pdi-plan.md)을 우선합니다. 아래 내용은 초기 제안 기록이며, 구 팝클 고정축과 일곱 고정 등급을 현재 구현 기준으로 사용하지 않습니다.

상태: `Proposed` · 작성일: 2026-09-23. 설계 단계이며 기능 구현과 실제 데이터 검증은 아직 수행하지 않았다. 아래 정책·테이블·API는 구현 제안이며 확정된 계약이 아니다.

## 목표와 범위

- 구 팝클과 클리어 보유 기록으로 같은 레벨의 채보 난이도를 추정한다.
- 화면은 하 / 중하 / 중 / 중상 / 상 / 별격 / 개인차를 제공한다.
- 추후 유저 투표로 기여하고 자신의 표를 수정·철회할 수 있게 한다.
- 본인의 메달·점수를 겹쳐 보고 PNG로 저장한다.
- 대상 백엔드 저장소 `popngg`는 Spring 서버다. 화면과 PNG 생성은 별도 프런트엔드 작업으로 분리한다.

## 확인한 기존 구조

- domain / application / infra / api 모듈과 Flyway 마이그레이션을 사용한다.
- PopclassPolicy에 구 팝클 계산 함수가 있고 user_profiles에 legacy_popclass가 있다.
- PlaydataQueryService와 PlaydataQueryResults가 채보 ID, 레벨, 메달, 버전별·전체 최고 점수를 제공한다.
- 기존 메달 문서와 현재 계산 코드의 범위가 다르므로 문서의 숫자 범위를 그대로 클리어 판정에 쓰지 않는다.
- 마이그레이션 번호는 구현 시 백엔드 저장소의 최신 상태를 확인해 정한다.

## 1단계: 데이터와 판정 기준 확인

읽기 전용 집계로 레벨별 채보 수, 유효 유저 수, 채보별 플레이·클리어 수, 팝클 분포, 기록 갱신 시점을 확인한다.

- legacy_popclass가 이관 당시 고정값인지 현재 구 공식으로 갱신되는 값인지 실제 쓰기 경로를 추적한다. 고정값이면 그 시점의 기록을 확보하거나 동일 스냅샷의 기록으로 구 팝클을 재계산한다. 서로 다른 시점의 값을 무조건 섞지 않는다.
- 기본 제안은 일반 클리어 이상을 성공으로 삼는다. EASY CLEAR와 LONGOFF CLEAR는 별도 상태로 보존하고 최초 모델의 성공·실패 표본에서 제외한다. 최종 정책은 실제 메달 의미 확인 후 고정한다.
- 미플레이와 알 수 없는 메달은 실패로 처리하지 않는다. 유저·채보당 한 기록만 사용한다.
- BOT, 삭제 채보, 유효하지 않은 팝클은 제외한다. 팝클 산출 대상 50개 미만 유저는 별도 집계해 영향을 확인한다.
- 비공개 유저는 초기 통계에서 제외하고, 자신의 비공개 기록 조회는 기존 권한 정책에 맞춘다.
- 게임 버전·레벨 변경·UPPER 등 별도 채보를 구분한다. 현재 레벨과 채보 ID를 기준으로 하되 산정 시점의 레벨도 저장한다.

완료 조건: 메달 판정표, 사용 가능한 표본 현황, 팝클 기준 시점이 문서화되어야 한다. 실제 데이터 접근이 없다면 이 단계 결과는 미확인으로 남긴다.

## 2단계: 자동 서열 산정

구 팝클 구간별로 플레이 유저 수와 클리어 보유율을 집계하고, 팝클이 높을수록 클리어 확률이 증가하도록 단조 보정한 곡선을 만든다. 50%를 통과하는 팝클을 난이도 지표로 추정한다.

- 이 값은 최초 클리어 당시 실력이 아닌 현재 기록상 클리어 보유율의 지표다. 플레이한 사람만 포함되는 선택 편향도 남는다.
- 표본 수, 팝클 구간 커버리지, 재표집에 따른 추정 변동을 함께 저장한다.
- 전원 성공·전원 실패, 50% 교차점 부재, 적은 표본, 지나치게 큰 추정 변동은 판정 보류로 둔다. 무리한 외삽은 하지 않는다.
- 하~상은 레벨별 기준 팝클 경계로 분류한다. 데이터 조사 후 경계를 보정·고정하고 알고리즘 버전에 포함한다. 곡 수를 무조건 다섯 등분하지 않는다.
- 별격은 상의 경계를 뚜렷하게 벗어나는 경우만 후보로 삼고 인접 레벨과 대조한다. 모든 레벨에 별격을 강제로 만들지 않는다.
- 기록만으로 개인차를 확정하지 않는다. 개인차 초기 지정은 검토 결과로, 추후에는 별도 투표 결과로 반영한다.
- 결과는 초안으로 생성하고 검토 후 공개한다. 실패하면 기존 공개본을 유지한다.

완료 조건: 표본이 충분한 레벨에서 산정 보고서를 검토하고, 동일 입력·정책으로 동일 결과를 재현할 수 있어야 한다.

## 3단계: 저장 구조와 조회 API

추가 테이블 제안:

| 테이블 | 역할 |
| --- | --- |
| tier_snapshots | 게임 버전, 데이터 기준일, 알고리즘·정책 버전, 투표 마감 시점, 초안/공개 상태 |
| chart_tier_entries | 스냅샷·채보별 레벨, 추정 팝클, 표본·신뢰도, 자동 등급, 투표 등급, 최종 등급, 개인차 여부, 보류 사유 |
| chart_tier_votes | 유저·채보·평가 범위별 난이도 선택, 개인차 선택, 수정 시각; 복합 UNIQUE로 중복 표 방지 |
| chart_tier_overrides | 운영자 보정값, 이유, 작성자, 적용 범위·시각; 자동 결과를 덮어 지우지 않음 |

개인차는 서열상의 최상위 값으로 저장하지 않는다. difficultyTier와 personalDifference를 분리하고, 화면에서는 개인차로 지정된 채보를 개인차 행에 한 번만 배치한다. 원래 난이도는 상세 정보에 유지한다. 판정 보류는 일곱 등급과 별도 상태다.

API 제안:

| 메서드·경로 | 용도 |
| --- | --- |
| GET /api/v1/tier-lists?level=…&snapshotId=… | 공개 서열표와 산정 기준 조회; ID 생략 시 최신 공개본 |
| GET /api/v1/me/tier-lists?level=…&snapshotId=… | 공개 서열표에 인증된 본인의 기록을 일괄 결합 |
| GET /api/v1/charts/{chartId}/tier-votes | 투표 분포와 집계 기준 조회 |
| PUT /api/v1/charts/{chartId}/tier-vote | 내 표 생성·수정 |
| DELETE /api/v1/charts/{chartId}/tier-vote | 내 표 철회 |

응답에는 snapshotId, 기준일, 채보 ID·곡명·이미지·난이도·레벨, 최종 등급·근거·개인차·보류 상태를 포함한다. 개인화 응답은 recordAsOf와 메달·점수 기준을 추가한다. 없는 기록은 null로 반환한다.

domain에 등급·클리어 정책, application에 산정·조회·투표 유스케이스, infra에 DB 집계·저장·실행 작업, api에 인증·입력 검증·응답을 배치한다. 전체 집계는 요청마다 실행하지 않고 별도 작업으로 수행한다. 공개본은 원자적으로 전환하고 이전 공개본으로 되돌릴 수 있게 한다. 개인화 응답은 공유 캐시에 넣지 않는다.

## 4단계: 서열표 화면과 PNG 저장 — 첫 출시 범위

- 레벨 선택, 일곱 분류 행, 판정 보류 영역, 채보 카드와 산정 기준을 표시한다.
- 로그인하면 내 메달과 전체 최고 점수를 표시한다. 미플레이를 명확히 구분하고 버전별 점수는 후속 옵션으로 확장한다.
- 닉네임·구 팝클·점수 표시 여부를 선택할 수 있게 한다.
- 화면과 내보내기가 동일한 데이터 모델과 카드 렌더러를 사용한다. 내보내기를 시작하면 서열 스냅샷과 개인 기록 응답을 고정한다.
- 프런트엔드에서 PNG를 생성한다. 전체 레벨 한 장을 기본으로 하고 긴 표는 분할 저장을 제공한다.
- 내보내기 전 글꼴·곡 이미지 로딩을 기다리고 실패한 이미지는 대체 카드로 표시한다. 이미지 CORS, 모바일 메모리, 캔버스 크기 제한을 검증한다.
- 이미지에 레벨, 서열 기준일, 기록 조회·갱신 시각의 의미, 출처를 넣는다. 공개 링크 생성은 첫 범위에서 제외한다.

완료 조건: 화면과 PNG의 채보·메달·점수가 일치하고, 긴 곡명·이미지 누락·모바일에서도 잘림이나 누락 없이 저장되어야 한다.

## 5단계: 유저 투표 — 후속 출시

- 로그인한 유저가 하~별격 중 하나를 선택하고 개인차 여부는 독립적으로 입력한다. 투표 없음과 개인차 아님을 구분한다.
- 기본 제안은 해당 채보의 플레이 기록 보유자에게 투표를 허용하되 클리어를 필수로 요구하지 않는다.
- 한 유저 한 표를 DB에서 보장하고 수정·철회를 지원한다. 구 팝클 가중치는 초기에는 적용하지 않는다.
- 난이도 대표값은 순서형 투표의 중앙값을 후보로 계산한다. 최소 표수·동률 처리·합의율·개인차 채택 비율은 정책으로 버전 관리한다.
- 표가 부족하거나 의견이 크게 갈리면 자동 등급을 유지하면서 투표 분포를 보여준다. 의견 분산만으로 개인차라고 확정하지 않는다.
- 초기에는 투표 결과로 변경안을 만들고 검토 후 새 스냅샷에 공개한다. 자동 반영은 충분한 운영 데이터 확보 뒤 추가한다.
- 레벨·채보 변경 시 과거 투표는 보존하되 새 평가 범위의 집계와 분리한다.

## 검증과 작업 단위

1. 데이터 조사와 정책 확정.
2. DB·도메인·산정 작업 및 보고서.
3. 공개·본인 서열표 API와 공개본 전환.
4. 프런트엔드 서열표·개인 기록·PNG 저장.
5. 투표 저장·집계·변경안 검토·새 공개본 반영.

필수 검증은 메달별 성공/제외/실패, 미플레이 제외, 중복 표본 방지, 표본 부족·교차점 부재, 등급 경계, 투표 수정·철회·동시 요청, 본인 기록 권한, 스냅샷 재현성과 전환 실패 복구다. DB 집계는 실제 사용하는 DB의 통합 테스트로 확인하고, 프런트엔드는 화면/이미지 일치와 모바일 내보내기를 확인한다.

첫 구현은 1~3단계로 서버 기반을 만들고 4단계를 연결한다. 투표는 저장 구조를 미리 고려하되 5단계에서 공개한다. 데이터 접근 가능 여부, 프런트엔드 저장소와 곡 이미지 제공 방식, 메달 판정 및 표본별 경계·투표 임계값은 구현 과정에서 확인할 항목이다.
